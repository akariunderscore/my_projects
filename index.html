chipped dice

65536 bytes out of crypto.getRandomValues, in your browser, one byte per pixel. it should look like static. if it looks like anything else, something is Very Wrong

what this is: a way to look. row y, column x is byte number y*256+x, drawn as grey level 0..255. chip the die throws away every 0 and rerolls it, which is roughly the shape of the "this rng can never emit zero" bug. costs about 0.006 bits per byte. try spotting it in the static above (you can't)

sticky bit is the other kind of broken: no value goes missing, but on about 2% of bytes the lowest bit gets forced to 1. every face still shows up, so the pair plot's red and the histogram's red bars have nothing to say. the pooled monobit row notices, slowly (one roll sits around z = 1.8, a shrug; by five rolls it's red and staying red). chi-square gets there first, red somewhere around roll four. runs mostly doesn't move, which is sort of the lesson: each test is a different-shaped hole to fall through

what this isn't: an audit. a good backdoored generator looks exactly like static to every test on this page, that's the whole point of it being good. what eyeballs and boring stats can catch is a missing face on the die, a stuck bit, a value that never shows up. that's a much smaller claim, but it's the one you can check yourself

pair plot (pooled over every roll)

every byte and the one after it make a point: x is the first, y is the second. 65535 pairs per roll into 65536 cells, so one roll is basically noise. brightness is how far each cell's count sits from expected (mid grey = spot on). once there's enough data that an honest empty cell is ~impossible (16 rolls, roughly 1 in 135 odds of even one false alarm), any cell that has never been hit goes red. a missing value can't hide here: it's a whole row and a whole column (for a chipped die that's the top row and the left edge, hit re-roll x10 twice and watch them light up)

byte histogram (pooled over every roll)

raw counts would just be 256 identical-looking bars, so each bar is how far that value's count sits from expected, in standard deviations (dashed lines at ±3). fair die: grass, mostly inside the lines, no pattern. a value that has never shown up gets a full-height red bar, because that's the one you came here for (sticky bit gives you a comb instead: odd values lean up, even lean down, very faint until the pool is huge)

testgotfine if roughly

z-scores: |z| under ~2.6 is boring (good), and one in a hundred honest rolls will land outside that anyway, so a single yellow is a shrug. red that stays red as the pool grows is the interesting kind. runs counts places where the bitstream flips 0→1 or 1→0 (msb first within each byte), which catches bits that are too sticky or too jittery even when the ones/zeros balance is fine
